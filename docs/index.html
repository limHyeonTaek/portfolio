개요

후불 여행·보험·휴대폰·렌탈 상담을 받는 대외 사이트입니다. 운영 주소는 플랜잇.com 입니다.

Next.js 15 정적 내보내기를 S3 + CloudFront 로 배포합니다. 피그마 시안을 웹·모바일 두 벌로 옮긴 여행 랜딩 시리즈, 상담 접수 폼, 픽셀·분석 계측을 구현했습니다.

여행 목적별 랜딩(신혼·우정·가족)과 인스타그램 캐러셀에서 들어오는 링크 허브·월 납부금 계산 플로우까지 운영에 올렸습니다.

10월 말부터는 효도여행·보험 B2B 시상여행 랜딩, 네이버·카카오 소셜 로그인, 견적 일정표 짧은 주소(/q/번호)와 모두투어 사진 자동 삽입·미리보기를 더했고, 렌탈+동남아 랜딩(LP-10)을 만들고 있습니다(진행 중).

역할

  • 페이지 설계·구현: 홈, 여행 목록·상세, 여행 랜딩 시리즈, 링크 허브·월 납부금 플로우, 로그인·마이페이지, 휴대폰·렌탈·인터넷·보험 페이지
  • 어드민 견적 도구: 견적번호 발급, 견적서 전용 주소, 고객 일정표 짧은 주소·사진 자동 삽입·미리보기
  • 피그마 시안 코드화: 웹 1440·모바일 390 두 벌, 스크롤 모션 포함
  • 상담 접수 폼과 전산 연동(접수 API 는 전산 백엔드가 제공)
  • 계측: 메타 픽셀, GA4, Clarity, 네이버 분석, 유입 경로 수집
  • 배포·인프라: GitHub Actions(OIDC) → S3 + CloudFront, CloudFormation

기술적으로 고민한 점

정적 내보내기와 랜딩 페이지의 공존

서버 없이 S3 + CloudFront 로 서비스하려고 output: 'export' 를 썼습니다. 요청 시점 렌더링이 없으므로 랜딩 경로는 카테고리별 정적 경로 11개(/travel/lp/<slug>/)로 빌드 때 미리 만듭니다.

상담 접수처럼 서버가 필요한 동작은 전산 백엔드의 플랜잇 API 로 넘겨, 사이트 자체는 정적 파일로만 유지합니다.

메타 픽셀 Lead 중복 제거

Lead 이벤트는 광고 최적화의 학습 신호입니다. 버튼을 누른 시점이 아니라 서버가 접수 성공을 응답한 뒤에만 한 번 보내고, eventID 를 함께 보내 같은 접수가 두 번 집계되지 않게 했습니다.

카카오 SDK 초기화 순서와 폴백

카카오 JS SDK 는 외부 스크립트라 로드가 끝나기 전에 공유 버튼이 눌릴 수 있습니다. SDK 로드 → 초기화 → 공유 호출 순서를 지키고, SDK 를 쓸 수 없는 환경에서는 navigator.share, 그것도 없으면 클립보드 복사로 이어지게 했습니다.

빌드 변수로 분석 ID 주입, dev 제외

픽셀·GA4·Clarity·네이버 분석 ID 는 코드에 적지 않고 빌드 변수로 주입합니다. dev 빌드에서는 분석 스크립트를 넣지 않는 규칙을 둬 테스트 트래픽이 운영 데이터에 섞이지 않게 했습니다.

시안과 픽셀 단위로 맞추는 검증

피그마 MCP 로 시안의 수치를 읽어 옮긴 뒤, 헤드리스 Chrome 으로 1440·390 화면을 캡처해 같은 폭의 시안과 구간별로 비교합니다. 어긋난 구간을 찾아 고치고 다시 캡처하는 과정을 반복합니다.

공유 링크로 그대로 다시 여는 계산 결과

월 납부금 플로우는 한 페이지 안에서 01~04 단계를 바꿔 그리지만, 지금 단계와 고른 값(여행지·인원·시기)을 주소의 쿼리에 함께 담습니다.

그래서 03 결과 화면을 카카오톡으로 보내면 받은 사람도 같은 결과 화면을 바로 엽니다. 여행지별 1인 월 금액은 여행 목록과 같은 상품 데이터·계산을 써서 페이지마다 숫자가 어긋나지 않게 했습니다.

정적 사이트에서 새 견적번호 열기

사이트가 정적 파일이라, 어드민에서 새로 발급한 번호에는 그 번호의 일정표 파일이 없습니다. 그래서 새 번호의 고객 링크를 공용 화면 하나로 모으고, 그 화면이 주소에서 번호를 읽어 서버에 저장된 일정 스냅샷을 불러오게 했습니다.

고객에게 보내는 주소는 /q/번호 로 줄이고, CloudFront 함수가 이 요청에 공용 화면을 돌려줍니다. 운영에는 CloudFront 함수 변경을 먼저 적용한 뒤 사이트를 승격합니다. 순서가 바뀌면 그 사이에 복사한 /q/ 링크가 404 가 되기 때문입니다.

발급 전에 보는 미리보기

미리보기는 번호 발급 때와 같은 함수로 스냅샷을 만들어 브라우저 localStorage 에 담고, 새 탭의 고객 화면이 서버 대신 그 값을 같은 정규화로 그립니다. 그래서 미리보기와 실제 고객 화면이 어긋나지 않습니다.

어드민에서 다시 누르면 storage 이벤트로 열린 탭이 새로고침 없이 바뀌고, 맨 위 배너에 저장되지 않은 화면이라는 점과 발급 전 점검에 걸린 항목을 보여 줍니다. 주소에 번호가 있는 고객 링크는 미리보기로 열리지 않습니다.

로그인 콜백 값이 분석 도구로 새지 않게

소셜 로그인 콜백 주소에는 1회용 code·state 가 붙어 옵니다. 네이버 분석 스크립트는 React 보다 먼저 현재 주소를 보내므로, 루트 레이아웃 <head> 맨 앞의 인라인 스크립트가 콜백 페이지에서만 이 값을 주소창에서 먼저 지웁니다.

콜백 교환은 한 문서에서 한 번만 해서, 개발 모드에서 effect 가 두 번 돌아도 1회용 state 로 보낸 두 번째 요청이 실패하지 않게 했습니다.

기술적으로 고민한 점

제외 집합으로 관리하는 dev → 운영 승격

dev 에는 기능이 계속 쌓이지만, 모든 기능이 같은 시점에 운영에 올라가지는 않습니다.

승격할 때마다 promote/<날짜> 브랜치를 만들고, 아직 운영에 올리지 않을 기능의 파일을 제외 집합(백엔드 146개·프런트엔드 54개 파일)으로 묶어 빼고 올립니다.

운영에 올릴 범위를 승격 시점에 고를 수 있고, 이 방식으로 19차 승격(2026-11-06)까지 진행했습니다.

사이트 접수를 전산 업무로 바꾸는 동기화

플랜잇 사이트의 접수(site_inquiry)는 그대로 두면 상담 업무로 이어지지 않습니다.

접수가 들어오면 고객과 상담 케이스를 자동으로 만들고, UTM·referrer 로 유입 매체를 분류합니다.

담당자가 정해지지 않은 접수는 인앱 알림·웹푸시·Mattermost 로 알려 놓치지 않게 했습니다.

환경별로 다른 배포 경로

dev 는 EC2 한 대에서 docker compose 와 Caddy 로 빠르게 반영하고, 운영은 ECR 이미지를 ECS 에 배포한 뒤 헬스체크로 확인합니다.

ci.yml (테스트)

    1. deploy-dev.yml
    2. EC2 · docker compose + Caddy
  • 운영
    1. deploy-prod.yml
    2. ECR 이미지
    3. ECS 배포

두 경로 모두 ci.yml 테스트를 통과한 코드만 받습니다. Terraform 저장소는 VPC·ALB·RDS 설계 초안 단계이며, 운영 배포는 GitHub Actions 파이프라인이 맡습니다.

테스트 비중

백엔드 Java 코드의 절반이 테스트이고 JUnit 5,459건, 프런트엔드 테스트 1,973건이 있습니다.

업종 5개와 역할별 권한이 얽힌 도메인이라 기능을 더할 때 기존 동작이 깨지지 않았는지 테스트로 먼저 확인합니다.

정적 사이트를 위한 공개 조회 API

플랜잇 사이트는 정적 파일이라, 어드민에서 새로 발급한 견적번호의 일정은 서버에서 읽어야 합니다.

저장 API 는 일정 JSON 을 해석하지 않고 번호 형식, 본문 크기(64KB), JSON 객체인지만 확인한 뒤 정해 둔 최상위 키만 남겨 번호별로 덮어씁니다. 공개 조회는 저장한 스냅샷을 캐시 없이 그대로 돌려주고, 저장되지 않았거나 형식이 틀린 번호는 오류 코드가 있는 404 로 답합니다.

저장 API 는 404·405 를 내지 않게 했습니다. 프런트가 이 둘을 「API 가 아직 배포되지 않음」으로 읽기 때문입니다. 본문은 스트림으로 상한 + 1바이트까지만 읽고, 권한 판정은 본문을 읽기 전에 합니다.

외부 API 응답에서 사진만 골라 싣기

모두투어 견적 상세에 쓰는 세 응답(상품 상세·일정·호텔)에는 사진 주소가 이미 들어 있었지만 읽지 않고 있었습니다.

대표 사진·일차별 관광지·호텔 사진을 각각 상한을 두고 매핑하되, 일정에서 빠지는 항목(선택관광 안내·식사·숙박·숨김)의 사진은 빼서 포함되지 않은 일정이 포함된 것처럼 보이지 않게 했습니다. 구글 장소·외부 호텔 DB 사진은 라이선스 때문에 싣지 않습니다.

세 칸은 따로 감싸 사진 매핑이 깨져도 기존 칸은 그대로 나갑니다. 테스트 픽스처는 실제 응답에서 매퍼가 읽는 키만 남겨(화이트리스트) 직원 식별 칸 같은 값이 저장소에 들어가지 않게 했습니다.

렌탈 변경분에서 「키만 바뀐 것」 가려내기

렌탈사 원본 엑셀은 달마다 시트 이름·열 순서·상품명 꼬리표가 바뀝니다. 업로드 양식 변환은 열 문자를 박지 않고 머리글 문구로 열을 찾고, 처음 보는 시트나 머리글이 나오면 종료 코드로 멈춰 사람이 규칙을 정하게 했습니다.

전월 대비 변경분은 상품 키로 신규·삭제·수수료 변경을 나누고 「이전 − 삭제 + 신규 = 새」 같은 등식을 검증합니다. 상품명 꼬리표만 바뀌어도 삭제 + 신규로 잡히므로, 같은 렌탈사의 삭제·신규 행을 모델명 + 의무개월로 짝지어 「키 글자만 바뀐 것」과 「진짜 빠진 것」을 따로 보여 줍니다.

  • Lead 전환 최적화: 플랜잇 픽셀의 Lead 이벤트를 최적화 목표로 씁니다. 이벤트는 사이트에서 상담 접수가 성공했을 때만 한 번 발생합니다.
  • 페르소나 기반 타깃·카피: 여행 목적별 페르소나 문서 6종을 기준으로 타깃과 문구를 정합니다.
  • 표현 규칙: 「무이자」「0원」「최저가」는 쓰지 않습니다. 조건이 붙는 가격은 「1인」「개월」을 함께 적습니다.
  • 동적 UTM: 새 광고에는 utm_source={{site_source_name}} 를 비롯해 노출 위치({{placement}})·광고 이름({{ad.name}}) 같은 동적 값을 반드시 붙입니다.
  • 세트 구조 조정: 노출 위치·연령 분석 결과로 Audience Network 를 제외하고, 연령을 고정하고, 피드와 릴스를 별도 세트로 나눴습니다.
  • 여행 목적별 캠페인: 신혼여행(LP-04)에 이어 우정여행(LP-06)·가족여행(LP-07)·효도여행(LP-05) 캠페인을 더했습니다. 캠페인마다 해당 페르소나의 연령대로 타깃을 고정하고 그 랜딩으로 보냅니다. 동남아 가성비 소재도 더했습니다.
  • B2B 캠페인: 보험 B2B 시상여행 랜딩으로 보내는 캠페인과 영업조직 대상 캠페인(2026-11-03)을 따로 엽니다. 영업조직 1차는 타깃 연령을 고정하고 성과가 낮은 소재를 일시정지하는 식으로 재편했습니다(2026-11-05).
  • 목표·예산 설계: 신혼 3차는 총예산으로 잡고 저녁 시간대에만 노출하는 스케줄(day-parting)을 붙였습니다. 우정·가족 2차는 잠재고객 목표에서 브랜드 인지도 목표(도달·빈도 제한)로 바꿨습니다.
  • 노출 위치별 광고 세트: 캠페인마다 피드(정사각) 세트와 릴스·스토리(세로) 세트를 따로 두고, 규격에 맞는 소재를 각각 붙입니다.
  • 소재 파이프라인: 피그마 섹션 → export → 메타 업로드. 2026-11-03부터 로컬 업로드 경로(업로드 세션 발급 → resumable POST → finalize)를 이미지·영상 모두에 써서 S3 를 거치지 않습니다.
  • 자동 음악: 새 소재는 Advantage+ 크리에이티브의 자동 음악(music_generation)을 켜서 등록합니다.
  • 성과 분석 리포트: 픽셀 Lead 기준 결과를 연령·성별·노출 위치·일자별로 나눠 보고, 전산에 들어온 접수와 맞춰 본 뒤 다음 타깃·세트 구조를 정합니다.
  • 보고서·퍼널 분석: 누적 성과 보고서(2026-11-03)와 B2B 퍼널 분석(2026-11-05)을 피그마 페이지에 정리했습니다. 연령·성별·노출 위치·소재별로 나누고, 랜딩 조회 → 접수 전환율을 함께 봅니다.
  • 준비 중인 캠페인: 렌탈+동남아(LP-10) 비교형 이미지 소재와 영상 캠페인을 만들어 두고, 랜딩이 운영에 반영되면 게시합니다(2026-11-06, 진행 중).

기술적으로 고민한 점

광고와 실제 접수 건을 잇는 추적

광고 관리자의 전환 수만으로는 어떤 접수가 어느 광고에서 왔는지 전산에서 알 수 없습니다.

그래서 동적 UTM 을 광고 URL 에 붙이고, 사이트가 UTM·referrer 를 접수와 함께 전산으로 보내도록 했습니다.

전산은 이 값으로 유입 매체(ig/fb)를 분류하고 광고 이름·노출 위치까지 기록합니다.

학습 신호로 쓸 수 있는 Lead 이벤트

최적화 목표가 Lead 이므로 이벤트가 빠지거나 두 번 잡히면 학습이 흔들립니다.

Lead 는 서버가 접수 성공을 응답한 뒤에만 한 번 보내고, eventID 를 붙여 같은 접수가 중복 집계되지 않게 했습니다.

노출 위치·연령 분석에 따른 세트 재구성

노출 위치·연령별 결과를 나눠 본 뒤 Audience Network 제외, 연령 고정, 피드·릴스 세트 분리로 구조를 바꿨습니다.

소재는 피드용 정사각(1080)과 릴스용 세로(1080x1920) 두 규격으로 준비합니다.

광고 문구의 표현 규칙

후불 여행은 월 납부 금액이 눈에 띄는 상품이라 오해를 부르는 표현이 생기기 쉽습니다.

「무이자」「0원」「최저가」는 금지하고, 조건부 가격에는 「1인」「개월」과 적용 조건을 함께 적는 규칙을 두고 카피를 쓸 때마다 점검합니다.

노출 위치별 소재를 세트 분리로 대신하기

한 광고에 노출 위치마다 다른 소재를 붙이는 기능은 지금 쓰는 MCP 로는 열려 있지 않습니다.

그래서 같은 타깃의 광고 세트를 피드용과 릴스·스토리용으로 나누고, 피드 세트에는 정사각 소재, 릴스·스토리 세트에는 세로 소재를 붙였습니다.

고칠 수 없는 크리에이티브

자동 음악 같은 크리에이티브 기능은 만든 뒤에 바꿀 수 없습니다.

기능을 바꿀 때는 크리에이티브와 광고를 새로 만들어 켜고, 이전 광고는 일시정지해 둔 뒤 정리합니다.

성과를 나눠 보는 기준

결과는 연령·성별·노출 위치·일자 네 축으로 나눠 봅니다. 같은 캠페인 안에서도 연령·성별·지면에 따라 반응이 달라질 수 있어서, 합계만 보고는 무엇을 바꿀지 정하기 어렵습니다.

결과가 기대와 다르면 먼저 계측 경로(같은 접수 폼·같은 Lead 이벤트)가 다른 랜딩과 같은지 확인해 기술 결함을 배제하고, 그다음 소재·타깃을 봅니다.

시간대 스케줄과 예산 유형

저녁 시간대에만 광고를 내는 스케줄은 총예산 캠페인에서 걸 수 있습니다. 그런데 게시된 캠페인은 예산 유형(일예산 ↔ 총예산)을 바꿀 수 없습니다.

그래서 예산 유형을 바꿔야 할 때는 기존 캠페인을 고치지 않고 새 캠페인으로 만들어 옮깁니다.

MCP 로 운영하며 정한 규칙

타깃이나 예산을 고치면 광고 세트가 일시정지되는 경우가 있어, 수정 절차에 다시 켜는 단계와 상태 확인까지 넣었습니다.

Advantage+ 오디언스는 기본으로 켜 두고, 사용자가 명시적으로 끄라고 하거나 연령 제한을 반드시 지켜야 할 때만 끕니다.

관심사 타깃은 ID 를 찾는 검색 도구가 없어 임의의 ID 를 넣지 않습니다. 인스턴트 양식은 페이지의 약관 수락이 먼저 되어 있어야 만들 수 있습니다.

랜딩 문제와 소재 문제 나누기

광고 지표 옆에 랜딩 조회 → 접수 전환율을 함께 둡니다. 클릭과 랜딩 조회는 들어오는데 접수로 이어지지 않으면 랜딩을, 클릭부터 적으면 소재·타깃을 먼저 고칩니다.

누적 성과 보고서와 B2B 퍼널 분석을 이 기준으로 연령·성별·노출 위치·소재별로 나눠 정리했습니다.
